# 聊天事件分析调度

默认按北京时间每小时开启一轮，同时恢复超时任务与到期重试；事件任务不再每五分钟巡检。
单次执行在消息数与时间预算内消费该用户同一空间的多个会话，达到预算后等下一个整点续跑。
排队时固定任务所属空间，群和消息清单在真正领取执行权时确定；
Worker 真正领取执行权后，按已完成上传且解析成功的 `UploadBatch` 选择最新未处理消息，
正在上传、解析或失败的批次不进入分析。解析消息、来源与批次完成状态在同一事务提交，
不会读取半批数据；重复上传通过已有消息唯一分配去重。
不按消息发生时间丢弃旧消息，因此排队期间晚上传的历史聊天也会被纳入。

## 执行边界

- 用户键统一为 `AnalysisJob.created_by_id`，即 Devify 账号；自动任务使用上传者，
  手动任务使用发起者，重试不改变原任务所属用户。空间权限仍逐任务校验。
- 一个用户最多占用一个执行槽位，槽位包含已投递但尚未开始的任务。
  其他会话请求保存在原有 `AnalysisJob` 中等待，不提前向 Celery 投递。
- 自动调度每次只为一个用户建立一个待领取记录；`snapshot_pending=true`、输入范围暂为 0，
  会话外键仅为候选路由，领取时可在原空间内重新选择群；任务不切换空间。
  同账号在其他空间的历史上传保留，在后续独立批次中处理。未分配原始消息就是待处理进度。
  真正开始后以 `input_boundary` 保存本批输入截止时间，消息清单由唯一分配表固定。
  单次用户执行内的后续会话固定在同一空间，沿用同一输入截止时间，后来完成的批次留到下轮。
  后续会话若失去执行机会重新排队，未领取的范围不提前固定，实际领取时再选最新批次。
  等待执行期间完成的批次仍会被纳入。完成后释放容量，让其他已排队用户继续执行。
  显式指定范围的手动任务保持用户指定的输入范围，不自动扩大。
- 同一空间的同一个 `request_key` 固定对应一个任务；不同 key 不自动合并。
  手动分析沿用指定范围，允许新 key 主动重新分析，不写入自动调度的消息分配表。
  自动任务继续通过 `AnalysisJobMessage` 唯一分配防止重复处理已上传消息。
- 待处理用户和可续跑的自动 PARTIAL 用户一起排序：优先从未获得批次或最久未获批次的用户，
  再应用每轮准入上限，避免按用户 ID 固定截取而长期遗漏其他用户。
- 用户槽位沿用任务租约和 fencing token，不引入第二套租约或检查点。
  槽位 0 仅串行化短暂的投递/领取事务；模型调用不持有这个数据库锁。
- 最终事件归并也占用同一用户槽位和全局容量，沿用原任务 fencing token；
  每个归并小批次后续租并保存原任务检查点，到时间预算后让出，模型判断从断点继续。
  过期五分钟的发布者不能写回。任务收尾优先发布本空间本轮结果，并使用剩余时间预算。
  整点恢复按时间预算继续发布已有候选；预算耗尽时保留进度到下一轮。
- 到达批次预算时，先提交当前消息块的结果、消息完成标记及检查点，然后释放执行权。
  正常让出不消耗失败重试次数；`resume_after` 防止重复投递提前恢复。
  模型暂时失败同样等下个整点，失败次数耗尽后终止；用户显式重试可以立即重新排队。
- 任务崩溃后由下一次整点任务接管，继续已提交进度；过期租约不能续租或写回结果。
  不会扫描并重新执行历史终态失败任务。

## 配置

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `CHAT_ANALYSIS_SCHEDULE` | `00:00,...,23:00` | 北京时间的新轮次时间，保留自定义时段支持 |
| `CHAT_ANALYSIS_MAX_CONCURRENT_USERS` | 直接运行/开发 `1`，生产 Compose `4` | 全局最多投递/执行的事件分析用户数，跨 Worker 生效 |
| `CHAT_ANALYSIS_BATCH_MESSAGES` | `1000` | 单次执行最多完成的消息数；自动任务也以此限制输入快照 |
| `CHAT_ANALYSIS_BATCH_SECONDS` | `120` | 单次执行的时间预算，在消息块之间检查 |
| `CHAT_ANALYSIS_DISPATCH_LIMIT` | `20` | 每次巡检最多为多少个用户建立待执行任务 |

时间预算不会中断正在进行的模型请求；块内仍由原模型超时与任务租约保护。
超长消息沿用原有片段检查点，时间预算可使片段间的续跑让出执行权。
并发上限只约束本调度器的聊天事件任务，不改变独立总结、问答或报告的调度。
生产 Compose 将同一个 `CHAT_ANALYSIS_MAX_CONCURRENT_USERS` 值传给 API、各 Worker 和调度器，
同时用它设置分析 Worker 的进程数，默认 4，可在部署 `.env` 中覆盖；开发 Compose 仍为单进程。
每轮准入上限 `CHAT_ANALYSIS_DISPATCH_LIMIT` 控制待执行用户数，与模型并发上限独立。
历史手动 PARTIAL 记录不做自动回填或游标重置，需要时单独人工处置。

## 发布

迁移 `0009_analysis_execution_slots` 仅新增执行槽位表，不修改事件与历史任务数据。
上线前需停止并排空旧版分析 Worker，再应用迁移并启动新版分析 Worker；
旧 Worker 不认识用户槽位，不能与新版调度器混用。回滚到不支持用户槽位的旧版时，
将 `CHAT_ANALYSIS_MAX_CONCURRENT_USERS` 临时设为 `1`，保持旧版的单进程执行方式。
若部署已有 `CHAT_ANALYSIS_SCHEDULE` 显式配置，应确认是否仍需保留原时段。
非整点时段会在随后整点检查时被接收，最多延后一小时。

迁移 `0010_hourly_analysis_schedule` 将存量默认的事件调度 `*/5` 调整为整点，
保留停用状态和管理员自定义时刻，不修改共享的五分钟时钟。总结、问答、报告的
超时巡检与上传恢复保留原频率，不触发事件重试。

升级时已有 RUNNING 任务即使没有槽位也计入容量；超时恢复保留已提交检查点。
默认部署脚本先停止旧版分析 Worker；自行增加的旧副本也必须停完再启动新版。
回滚前脚本停止调度器与分析 Worker，并在当前 API 执行 `check_analysis_handoff`：
有运行中任务或尚未固定输入的排队任务则拒绝回滚，并恢复当前版 Worker 与调度器。
因此不会让旧版消费范围为 0 的新任务。可先停止新任务入队、让现有任务完成后再回滚。
