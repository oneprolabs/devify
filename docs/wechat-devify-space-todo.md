# Devify 空间化与多人 AI 总结 TODO

> 状态：待实现
>
> 目标：在不破坏现有个人邮箱 AI 总结链路的前提下，引入 `Space`，支持个人空间和团队空间，并让邮箱、微信、WhatsApp、LINE 等来源、AI 配置、总结结果和成员权限统一归属于团队空间。
>
> 范围：Devify 服务端、Devify Web、`wechat-devify-tauri` 上传客户端，以及多渠道导入和事件工作台的后续接入。

## 0. 当前建议基线

- [ ] 产品概念统一使用 `Space`，首版不同时引入 `Tenant`、`Organization` 两套边界。
- [ ] 每个用户自动拥有一个个人空间；全局管理员配置普通用户是否可以创建团队空间。
- [ ] 一个用户可以只使用个人空间，也可以加入多个团队空间；同一用户在不同空间的角色独立。
- [ ] 全局管理员配置每个空间最多可邀请的其他用户数量；计数口径和配置作用范围待定。
- [x] 全局 `admin` 与空间成员角色分层；空间角色采用 `owner`、`maintainer`、`user`、`guest`，`maintainer` 是空间管理员。
- [ ] 原始邮件、微信消息、附件、Note、Event、Report 都必须属于一个空间。
- [ ] 上传或复制到空间的数据对该空间所有有效成员可见，不按上传者设置空间内私有数据；个人空间默认只有本人，不表示互联网公开。
- [x] 空间数据仅上传者和空间管理员可删除；`maintainer` 视为空间管理员。
- [x] 跨空间操作只复制资源，源资源保留，不修改源空间或目标空间属性；成员退出后空间数据保留。
- [x] 允许团队空间没有成员，后续由全局 `admin` 接管或分配。
- [ ] 个人配置和空间配置分离：AI 处理规则属于空间，界面和个人视图偏好属于用户。
- [ ] 现有账单、报销等非聊天业务暂不整体迁移到空间，先保持用户归属。
- [ ] 现有个人邮箱功能必须继续可用，迁移采用兼容和可回滚方式。
- [ ] 空间不直接绑定某一种渠道；服务端邮箱来源可绑定空间，本机聊天账号不必固定绑定空间，由用户上传时选择目标空间。
- [ ] 一个桌面客户端使用一个 Devify 登录会话，复用所有本机采集渠道和有权限的空间；不按渠道或空间单独签发 Devify token。
- [ ] 所有渠道进入统一的 `Source → Ingest → Normalize → Conversation/Message → Note → Event → Report` 链路。
- [ ] 渠道差异通过适配器和能力声明表达，不把 WhatsApp/LINE 特殊字段硬编码到核心消息表。

## 1. 先决策：命名与权限契约

### 1.1 空间模型契约

- [ ] 确认 `Space` 字段：`id`、`name`、`kind`、可空 `owner_user_id`、`status`、`created_at`、`updated_at`；空成员空间不得依赖有效 owner 存在。
- [ ] 确认 `Space.kind`：`personal` / `team`。
- [ ] 增加约束：每个用户最多拥有一个 `personal` 空间；团队空间通过成员关系加入，可加入多个。
- [ ] 确认空间状态：`active` / `suspended` / `archived`。
- [ ] 确认空间删除策略：首版只允许归档，不物理删除邮件、附件和总结。
- [ ] 确认空间名称和 slug 的唯一范围：建议全局唯一 slug，名称允许重复。
- [ ] 将现有实现和设计中的 `tenant_id`、`tenant_membership` 统一改为 `space_id`、`space_membership`。

### 1.2 成员与角色契约

- [ ] 新增 `SpaceMembership`：`space_id`、`user_id`、`role`、`status`、`invited_by`、`joined_at`、`created_at`、`updated_at`。
- [ ] 增加唯一约束：`(space_id, user_id)`。
- [ ] 允许一个用户对应多条不同空间的成员关系；个人空间默认只有本人，加入团队空间不是使用产品的前提。
- [ ] 定义角色权限矩阵：
  - [x] `owner`：继承 `maintainer` 的全部权限，包括管理成员、邮箱来源、AI 配置、空间设置和删除空间任意资源；另外负责转移所有权、归档空间和生命周期管理。
  - [ ] `maintainer`：空间管理员；管理成员、邮箱来源、AI 配置和空间设置，可删除空间数据。
  - [ ] `user`：建议可查看、上传、启动/重试处理和编辑业务结果；如为资源上传者可删除自己的数据。
  - [ ] `guest`：建议可查看数据；如为资源上传者且仍是有效成员，可删除自己的数据。
- [ ] `owner_user_id` 允许为空；最后一个成员或 owner 退出后空间可无有效成员，保留数据并进入待接管状态。
- [ ] 由全局 `admin` 接管/分配空成员空间，清理或更新失效 owner 关联并记录审计。
- [ ] 规定被移除成员的历史操作记录保留，但立即失去读取权限。
- [ ] 退出或被移除某个团队空间不影响个人空间和其他团队空间的成员关系。
- [ ] 全局 `admin` 读取或删除空间业务数据前必须先接管空间；接管及后续业务操作均记录审计，不得直接绕过空间权限。
- [ ] 不使用 Django `is_staff`、`is_superuser` 代替空间角色。

### 1.3 创建和加入策略

- [ ] 新用户注册时自动创建个人空间和 `owner` 成员关系。
- [ ] 现有用户通过数据迁移补建个人空间。
- [ ] 全局管理员设置普通用户是否可创建空间，并在服务端强制执行。
- [ ] 实现成员邀请、接受、拒绝、撤销和移除。
- [ ] 全局管理员设置空间最多可邀请的其他用户数；邀请创建、接受及并发操作时强制检查上限。

### 2.2 邮件归属调整

- [ ] 分享链接必须检查空间状态和成员权限；成员被移除不应继续获得新的空间内访问权限。

- [ ] 现有 `EmailAlias` 增加空间路由能力或新增空间级虚拟地址模型。
- [ ] 一条 IMAP 来源只能归属于一个空间，首版不支持同一邮箱复制到多个空间。
- [ ] 一个虚拟接收地址只能绑定一个空间。

- [ ] 保留个人邮箱地址的兼容读取和处理路径。
- [ ] 定义来源删除策略：停止接收不删除已经保存的邮件。

### 2.4 聊天导入模型调整

- [ ] `note`、`event`、`event_tag`、`topic_subscription`、`report` 增加 `space_id` 和创建者字段。
- [ ] `upload_batch` 增加 `space_id`、`uploaded_by_user_id`；数据访问范围由所属空间决定，不接受客户端指定空间内私有可见性。
- [ ] `analysis_job` 增加 `space_id`、发起者字段。
- [ ] `event_relation` 和人工活动审计表必须带 `space_id`。
- [ ] `message`、`message_part`、`message_origin` 通过父级会话/批次获得空间权限，不重复存储空间字段，除非查询性能验证确有必要。
- [ ] 重写唯一键和幂等键：
- [ ] 会话和消息去重键包含 `space_id` 和来源身份；个人空间与团队空间不得跨空间合并或因去重扩大权限。

  - [ ] `(space_id, request_key)`。
  - [ ] `(space_id, uploaded_by_user_id, request_key)` 用于上传幂等。

- [ ] 更新 `schema-examples.json`、SQL 示例、ER 图、验证结果和 README。

### 2.5 文件与附件权限

- [ ] `file_asset` 的底层 SHA-256 去重与空间归属分离，但任何业务下载仍必须回溯空间权限。
- [ ] 文件下载必须沿 `upload_item` / `EmailAttachment` 回溯到空间和 ACL。
- [ ] 禁止使用全局 `file_asset` ID 直接返回文件内容。
- [ ] 文件处理任务必须携带空间上下文和原始来源权限。
- [ ] 空间归档后禁止新增处理任务；历史附件按保留策略只读。

### 2.6 可扩展来源模型

- [ ] 定义统一来源元数据和导入记录；服务端直连来源可使用空间级 `SourceConnection` 保存连接配置，本机上传来源不要求持有服务端连接凭据或固定绑定空间。
- [ ] `channel_type` 支持 `email`、`wechat`、`whatsapp`、`line`、`other`；`provider` 表示 IMAP、Tauri 上传、官方 API 或文件导入等具体方式。
- [ ] 增加 `capabilities`：`live_sync`、`file_import`、`attachments`、`reply`、`search` 等。
- [ ] 增加 `external_account_key`，使用外部账号稳定标识，不使用展示名称作为身份键。
- [ ] 将服务端直连来源的凭据、游标和同步状态与消息内容分离；本机采集凭据留在客户端，不上传到 Devify。
- [ ] 对上传渠道复用统一的 `SourceImport` / `upload_batch`；不要为每个渠道复制一套批次表。
- [ ] 对实时渠道复用统一的 `IngestJob`、checkpoint、lease、fencing token 和失败重试语义。
- [ ] 允许同一本机账号的不同会话或范围投递到不同空间；每次明确确认目标，同一内容跨空间复制时保持独立权限和去重边界。
- [ ] 邮箱等服务端直连来源使用服务端适配器；桌面客户端内按需实现微信、WhatsApp、LINE 本地采集适配器，统一规范化和上传。
- [ ] 采集和解析适配器不负责空间权限；权限由服务端统一执行。WhatsApp/LINE 的读取方式、授权、平台限制和可用性须先验证，不假定已经支持。
- [ ] 统一来源元数据：`source_id`、`channel_type`、`provider`、`external_account_key`、`conversation_key`、`message_key`、`occurred_at`、`source_order`、`raw_locator`。
- [ ] 渠道特有字段放入受版本控制的 `source_fields` / `metadata`，核心查询字段保持稳定。
- [ ] 明确渠道能力缺失时的降级行为，例如只读导入时不显示回复、实时同步或已读操作。
- [ ] 为来源迁移、解绑、凭据轮换和删除建立审计记录；解绑不删除已保存的规范化消息。

## 5. 邮箱接收与 AI 处理链路

### 5.1 接收入口

- [ ] 将 IMAP 定时任务从“遍历用户邮箱”改为“遍历启用的邮箱来源”。
- [ ] 每个来源返回 `space_id`、来源 ID、空间配置版本和处理策略。
- [ ] 虚拟地址收到邮件时，按唯一别名解析到空间。
- [ ] 团队邮箱收到邮件时，邮件记录直接写入团队空间，不绑定某个普通成员。
- [ ] 个人邮箱继续写入对应个人空间。
- [ ] 同一个消息 ID 的去重范围改为空间范围，不能跨空间合并。
- [ ] 设计跨空间资源复制：源资源和两个空间的属性均不变；明确支持的数据范围、衍生结果、附件处理及审计，并提示目标空间成员可见。
- [ ] 增加资源复制 API/任务状态：校验源空间读取权和目标空间写入权，目标创建独立业务记录；复制操作者与原上传者的删除权限归属待确认。

### 5.2 保存与处理

- [ ] `EmailSaveService` 接受空间来源上下文，不再只接受 `user_id`。
- [ ] 保存邮件、附件和元数据时在同一事务中写入空间归属。
- [ ] AI 工作流启动参数携带 `space_id` 和配置版本。
- [ ] `WorkflowPrepareNode` 从邮件空间加载 Prompt、Issue、时区和处理策略。
- [ ] 邮件合并、相似度匹配和手工合并只能在同一空间内执行。
- [ ] 重试、强制重试和启动恢复任务必须重新检查空间是否有效以及成员/管理员授权。
- [ ] 处理暂停、失败重置、定时清理和任务锁都要按空间或来源隔离。
- [ ] 日志和任务追踪同时包含 `space_id`、`email_id`、`source_id`，避免只记录用户。

### 5.3 通知与结果

- [ ] 空间配置空间级通知渠道和通知接收人。
- [ ] 用户个人通知偏好只决定是否接收，不改变团队处理结果。
- [ ] 通知内容按空间权限过滤，不把其他空间的邮件摘要带入通知。
- [ ] 邮件详情、附件、总结、Issue、Todo 和分享链接全部使用统一空间权限服务。

### 5.4 多渠道统一处理链路

- [ ] 分别定义服务端直连适配器与客户端本地采集适配器的能力契约；共同遵循规范化消息、错误分类和能力声明，不假定本机采集支持服务端远程同步。
- [ ] 定义统一的导入结果：来源状态、批次状态、发现数、接受数、去重数、缺口数、失败项和下一游标。
- [ ] 规范化层将 Email、WeChat、WhatsApp、LINE 映射到同一套 `conversation`、`message`、`message_part`、`message_origin` 语义。
- [ ] 保留源平台原始定位信息，但不把源平台原始数据库、密钥或完整缓存上传到 Devify。
- [ ] 同一空间内可以跨渠道生成 Note/Event，但必须保留渠道和原文证据。
- [ ] 跨渠道自动合并只提出建议；没有人工确认或明确规则时，不把两个 Event 强制合并。
- [ ] AI 工作流读取统一消息结构和来源能力，不直接依赖 `email_*` 或 `wechat_*` 字段。
- [ ] 渠道特有的图片、引用、转发、语音、贴纸和文件都通过 `message_part` 及能力状态表达。
- [ ] 为每个来源记录时区、账号范围、同步时间窗和数据完整性缺口。
- [ ] 统一处理暂停、重试、限流、配额、幂等和审计，渠道适配器只提供具体执行逻辑。

## 9. 测试与验收

### 9.1 权限隔离

- [ ] 空间 A 成员无法读取空间 B 的空间详情、邮件、附件、总结、任务和报告。
- [ ] 按最终权限矩阵验证 `guest`、`user` 的读取、上传、处理和管理权限。
- [ ] `maintainer` 可以管理空间并删除数据，操作必须审计。
- [ ] 被移除成员立即失去访问权限，已有 token 不产生越权访问。
- [ ] 同一登录会话可向有上传权限的多个空间投递；成员被移除或空间停用后，续传、完成及重试不得继续写入。
- [ ] 同一来源分别上传或复制到个人和团队空间时，不因去重跨空间泄露；源资源和空间属性保持不变。
- [ ] 上传者及空间 `maintainer` 可删除对应数据，其他成员不能删除；测试降为 `guest` 的上传者及自动接收邮件。
- [ ] 最后成员退出后数据保留，管理员可接管并重新分配；设备授权可列出和撤销，设备数量不设上限。
- [ ] 用户可以只拥有个人空间，也可以同时加入多个团队空间；退出一个团队不影响其他空间。
- [ ] 空间内所有有效成员能查看该空间数据；非成员和被移除成员不能查看。
- [ ] 个人空间内容不会出现在团队空间列表、搜索、合并和报告中。

## 13. 主要风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 仍按 `user_id` 查询邮件 | 高 | 统一空间权限服务；禁止新接口直接按用户过滤业务数据 |
| 团队邮箱没有单一接收用户 | 高 | `EmailMessage` 增加空间归属和可空接收用户字段 |
| 同一邮箱被多个空间绑定 | 高 | 来源唯一约束和创建时冲突检查 |
| 空间配置覆盖全局配置不透明 | 中 | 配置解析顺序、版本和审计明确展示 |
| 团队 AI 费用归属不清 | 高 | 团队自动处理上线前先确定空间额度或计费 owner |
| 附件按全局文件 ID 越权读取 | 高 | 下载必须回溯来源空间并检查 ACL |
| 迁移导致个人历史数据丢失 | 高 | 幂等迁移、行数校验、备份和回滚脚本 |
| 事件跨空间关联 | 高 | 数据库关系和服务层同时校验 `space_id` |
| 只在前端保存当前空间 | 中 | API 使用显式空间路径，服务端每次校验成员关系 |
| 同时改造全站所有业务 | 中 | 先限定聊天和邮箱 AI 域，账单/报销暂不迁移 |

- [ ] 多人上传相同 Note 时，确定来源保留、生成幂等、相似 Note 提示、人工合并和单个上传者删除后的处理规则。
- [ ] 确认复制所需权限、复制后上传者归属、正在执行的 AI 任务和复制失败回滚规则。
- [ ] 空间默认页、客户端默认投递空间和多空间切换规则（建议每个客户端设备独立保存默认空间，但服务端每次校验成员权限）。

### 14.2 必须先定的技术契约

- [x] 使用现有登录体系；页面可查看和撤销设备授权，设备数量不限。
- [ ] 明确现有认证体系下的设备识别、短期 access token、refresh token 轮换、撤销生效方式和登出行为。
- [ ] 客户端最低支持版本和 API 版本兼容策略；空间字段变更期间旧版客户端如何处理。
- [ ] 上传批次的状态机、分片过期时间、取消/重试语义，以及相同幂等键但内容不同的冲突处理。
- [ ] 来源身份模型：本机渠道账号与目标空间解耦；服务端直连邮箱来源与空间绑定；来源账号变更、换设备和多设备重复采集如何处理。
- [ ] 消息编辑、撤回、删除、反应、时区变化和附件缺失如何表达；历史导入和增量导入是否使用同一消息模型。
- [ ] 数据库、对象存储、搜索索引、向量库、缓存、Celery/异步任务和通知是否全部携带 `space_id`，并逐项做越权测试。
- [ ] 空间复制和删除如何避免跨空间复用同一业务记录；底层文件去重与空间业务权限如何分离。

### 14.3 必须先定的业务和合规契约

- [ ] 团队 AI 调用由空间共享额度还是计费 owner 承担；重复任务、失败重试、附件解析和跨渠道分析如何计费。
- [ ] 额度耗尽时是继续保存原文、暂停 AI，还是拒绝接收；是否设置成员数、存储、附件和每日 AI 配额。
- [x] 成员退出空间后数据保留；允许空成员空间并支持全局 `admin` 后续接管或分配。
- [ ] 确认空间归档、成员移除、用户注销、误上传撤回和彻底删除的规则；备份、搜索索引和模型供应商侧数据如何同步处理。
- [ ] 数据保留期限、导出格式、删除证明、审计日志保留期限和空间 owner 失效后的接管规则。
- [ ] AI 供应商是否接收原始邮件/聊天/附件，是否保留数据，是否允许团队空间关闭外部模型处理；提示注入和敏感信息脱敏策略。
- [ ] 通知、邮件转发、分享链接是否始终继承空间成员权限，以及空间外分享是否一律禁止（建议首版禁止绕过空间成员权限）。
- [ ] 团队邮箱首版优先支持虚拟接收地址，还是优先支持共享 IMAP；邮箱来源由谁维护，来源凭据如何轮换。
- [ ] 是否需要空间级通知渠道，还是继续沿用全局 Threadline 通知渠道。

### 14.4 必须先做的渠道可行性验证
